End-to-End Session Tests for Media over QUIC Transport

Abstract

This document describes a set of end-to-end tests that exercise a Media over QUIC Transport (MOQT) relay through real client sessions. For each test it gives a short description, the inputs, the message flow as a call-flow diagram, and the expected outcome. The tests apply to MOQT draft-18 and later; results for several public relays are published in the moq-web interop report.¶

1. Introduction

Interoperability between MOQT [MoQTransport] implementations is best established by running the same scenarios against many relays and comparing what each one does. This document describes such a set of scenarios, for draft-18 [MoQTransport18] onwards. Each test drives one or more client sessions through a relay and checks only what is observable at those clients: the control messages they receive and the Objects delivered to them.¶

The tests are implemented in the moq-web session-e2e suite [MOQ-WEB], whose results for several public relays are published in [INTEROP-REPORT]. This document is a description of the tests, not of any implementation, and is intended to let other implementers reproduce them.¶

2. Conventions and Definitions

Pub:

A client session that publishes Tracks through the relay.¶

Sub:

A client session that subscribes to Tracks through the relay.¶

Relay:

The MOQT relay under test.¶

Client:

A single session in tests that need only one.¶

3. Test Environment

Each client opens its own MOQT session to the relay over WebTransport [WebTransport], offering the MOQT version under test. Unless a test says otherwise:¶

  • Track Namespaces are unique per test run, of the form moq-web-e2e/<profile>/<label>/<random>, so concurrent runs against the same relay do not interfere.¶

  • Object payloads identify the Object they belong to, so that every received Object can be checked byte for byte against the one sent. Tests 05 to 23 send generated chat payloads: the ASCII string msg-<G>-<O>-, padded to 64 bytes with a deterministic pattern. Test 15 sends obj-<i>, and tests 34 and later send the ASCII string g<G>/o<O> for the Object at Group G and Object ID O.¶

  • Two delivery profiles are used: "stream", which sends Objects on subgroup streams, and "datagram", which sends them as Object datagrams. Tests that run under both are marked as such.¶

  • A wait for a message or Object that does not arrive fails the test after the timeout given in the test.¶

  • Applicability names the first MOQT draft the test runs on; it runs on every later draft too. A test that depends on a feature added in a later draft is skipped for earlier ones.¶

4. Test Description Format

Each test is described with four parts:¶

Description:

What the test exercises and why, in a few sentences.¶

Inputs:

The parameters the test chooses: Tracks, counts, timings and options.¶

Call Flow:

The messages exchanged, in order. Arrows show the direction of a message; the relay is in the middle column. A message the relay forwards appears once on each side. Lines starting with * are actions or checks at that endpoint, not messages. On draft-23 a FETCH is answered by REQUEST_OK; call flows show it as FETCH_OK, the draft-22 name.¶

A range written G1/O1..G2/O2 runs from Object O1 of Group G1 to Object O2 of Group G2, inclusive. An end Object of 0 means the whole of Group G2: the FETCH carries no End Object.¶

Expected Outcome:

The conditions the test asserts. The test passes only if all of them hold.¶

5. Test Cases

5.1. Session Setup

Applicability:

draft-18 and later¶

Description:

A client opens a WebTransport session to the relay and completes the MOQT setup exchange. This proves that version negotiation and any authorization the relay requires work end to end. The setup path is the same for both delivery profiles.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • MOQT version: the draft under test¶

Call Flow:¶

 Client                   Relay
    |                       |
    * open WebTransport
    |---- CLIENT_SETUP ---->|
    |<---- SERVER_SETUP ----|
    * session ready
¶

Expected Outcome:¶

  • CLIENT_SETUP and SERVER_SETUP complete.¶

  • The session reaches the ready state.¶

5.2. Publish Namespace

Applicability:

draft-18 and later¶

Description:

A publisher sends PUBLISH_NAMESPACE for a fresh namespace. The relay must accept it.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Namespace: moq-web-e2e/<profile>/announce-<profile>/<random>¶

Call Flow:¶

   Pub                    Relay
    |                       |
    |- PUBLISH_NAMESPACE -->|
    |<----- REQUEST_OK -----|
¶

Expected Outcome:¶

  • The relay answers PUBLISH_NAMESPACE with REQUEST_OK.¶

5.3. Publish

Applicability:

draft-18 and later¶

Description:

A publisher sends PUBLISH for a Track that has no subscribers yet. The relay must accept it and the publisher must hold a Track Alias for the Track. The publisher does not wait for the relay to start forwarding.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Track: <namespace>/chat, publisher priority 128¶

Call Flow:¶

   Pub                    Relay
    |                       |
    |------ PUBLISH ------->|
    |<----- REQUEST_OK -----|
    * Track Alias known
¶

Expected Outcome:¶

  • The relay answers PUBLISH with REQUEST_OK.¶

  • The Track Alias is a non-negative integer.¶

5.4. Namespace Subscription

Applicability:

draft-18 and later¶

Description:

A subscriber sends SUBSCRIBE_NAMESPACE for a prefix, then a publisher announces a namespace under that prefix. The relay must tell the subscriber about the new namespace with a NAMESPACE message on the SUBSCRIBE_NAMESPACE request stream.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Prefix: moq-web-e2e/<profile>/nssub-<profile>¶

  • Namespace: the prefix plus one random field¶

  • Wait between SUBSCRIBE_NAMESPACE and PUBLISH_NAMESPACE: 200 ms¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |                       |<-SUBSCRIBE_NAMESPACE--|
    |                       |----- REQUEST_OK ----->|
    |                       |                       * wait 200 ms
    |- PUBLISH_NAMESPACE -->|                       |
    |<----- REQUEST_OK -----|                       |
    |                       |----- NAMESPACE ------>|
    |                       |                       * namespace seen
¶

Expected Outcome:¶

  • The subscriber receives NAMESPACE for exactly the announced namespace within 10 s. Namespaces left over from earlier runs are ignored.¶

5.5. Subscribe and Deliver

Applicability:

draft-18 and later¶

Description:

A publisher publishes a Track and a subscriber subscribes to it. The publisher then sends a run of Objects and the subscriber checks each one it receives against what was sent. On streams every Object must arrive, in order. Datagrams are not retransmitted, so a small loss is tolerated.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Track: <namespace>/chat, default subscription filter¶

  • Objects: 30 generated chat payloads of 64 bytes, 10 per Group (Groups 0 to 2)¶

  • Collection time: up to 20 s (stream), 8 s (datagram)¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |                       |<----- SUBSCRIBE ------|
    |                       |--- SUBSCRIBE_OK ----->|
    |                       |                       * wait 250 ms
    |== Objects 0/0..2/9 ==>|== Objects 0/0..2/9 ==>|
    |                       |                       * check each
¶

Expected Outcome:¶

  • Stream: all 30 Objects arrive, in Group and Object order, and none arrives more than once.¶

  • Datagram: at least 27 of the 30 Objects arrive (no more than 10% lost); the lost ones are reported.¶

  • Every received Object is byte-identical to the Object sent.¶

5.6. Pause and Resume

Applicability:

draft-18 and later¶

Description:

A subscriber pauses its subscription with REQUEST_UPDATE, then resumes it. Objects sent after the resume must reach the subscriber, showing that the relay restarts delivery. Objects sent while paused are not required to be delivered.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Objects: 30 generated chat payloads, 15 before the pause and 15 after the resume¶

  • Pause: REQUEST_UPDATE that stops forwarding (FORWARD 0 on draft-22, PAUSED on draft-23)¶

  • Resume: REQUEST_UPDATE that restarts forwarding¶

  • A relay may pass the pause on to the publisher. If it did, Pub waits up to 5 s for the relay to turn forwarding back on before sending the second 15 Objects, so they are not dropped at the publisher.¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |                       |<----- SUBSCRIBE ------|
    |                       |--- SUBSCRIBE_OK ----->|
    |===== 15 Objects =====>|===== 15 Objects =====>|
    |                       |                       * wait 500 ms
    |                       |                       * some arrived
    |                       |                       * pause:
    |                       |<--- REQUEST_UPDATE ---|
    |                       |----- REQUEST_OK ----->|
    |<-- REQUEST_UPDATE ----|                       |
    |   (optional: pause    |                       |
    |   passed on to Pub)   |                       |
    |                       |                       * wait 250 ms
    |                       |                       * resume:
    |                       |<--- REQUEST_UPDATE ---|
    |                       |----- REQUEST_OK ----->|
    |<-- REQUEST_UPDATE ----|                       |
    |   forward 1 / PAUSED  |                       |
    |   cleared (if paused) |                       |
    * wait up to 5 s for it |                       |
    |== 15 more Objects ===>|== 15 more Objects ===>|
    |                       |                       * more arrive
¶

Expected Outcome:¶

  • Some Objects arrive before the pause.¶

  • At least one Object arrives within 5 s of the resume.¶

5.7. Unsubscribe

Applicability:

draft-18 and later¶

Description:

A subscriber receives some Objects and then ends its subscription. On draft-22 and draft-23 this cancels the SUBSCRIBE request stream. Objects the publisher sends afterwards must not reach the subscriber.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Objects: 30 generated chat payloads, 15 before and 15 after the unsubscribe¶

  • Settle time after unsubscribing: 500 ms; observation time: 1 s¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |                       |<----- SUBSCRIBE ------|
    |                       |--- SUBSCRIBE_OK ----->|
    |===== 15 Objects =====>|===== 15 Objects =====>|
    |                       |                       * wait 500 ms
    |                       |<-- cancel SUBSCRIBE --|
    |                       |                       * wait 500 ms
    |== 15 more Objects ===>|                       |
    |                       |                       * wait 1 s
¶

Expected Outcome:¶

  • Some Objects arrive before the unsubscribe.¶

  • No Object arrives in the 1 s observation period after the settle time.¶

5.8. Track Status

Applicability:

draft-18 and later¶

Description:

A second session queries the status of a Track another session has published. The relay must answer the TRACK_STATUS request rather than leave it pending.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Track: <namespace>/chat, published 250 ms before the query¶

Call Flow:¶

   Pub                    Relay                    Req
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |                       |<---- TRACK_STATUS ----|
    |                       |- REQUEST_OK / ERROR ->|
¶

Expected Outcome:¶

  • The relay answers with REQUEST_OK or REQUEST_ERROR; either is a pass.¶

  • On REQUEST_OK, the Largest Location, when present, is a valid Group and Object.¶

5.9. Fetch from Cache

Applicability:

draft-18 and later¶

Description:

A publisher sends Objects with no subscriber, so the relay can only cache them. A second session then FETCHes a range and checks the returned Objects byte for byte. A relay that refuses FETCH is reported, and the test does not fail.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each); a large-payload variant runs on stream only¶

  • Default: 30 Objects of 64 bytes, 10 per Group; FETCH of 1/0..1/9 (10 Objects)¶

  • Large payload: 300 Objects of 2048 bytes, 10 per Group; FETCH of 0/0..29/9 (300 Objects)¶

  • Publisher Track property: max cache duration 60 s¶

  • Wait before the FETCH: 500 ms¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |====== Objects =======>|                       |
    |                       * cached
    |                       |<--- FETCH 1/0..1/9 ---|
    |                       |------ FETCH_OK ------>|
    |                       |=fetch stream Objects=>|
    |                       |                       * check each
¶

Expected Outcome:¶

  • Every Object in the range arrives within 10 s.¶

  • No Object outside the range arrives, and none arrives more than once.¶

  • Every Object is byte-identical to the Object sent.¶

  • If the relay answers the FETCH with REQUEST_ERROR, the test is reported as not supported rather than failed.¶

5.10. Fetch Cancel

Applicability:

draft-18 and later¶

Description:

A subscriber starts a large FETCH and cancels it as soon as the first Object arrives. On draft-22 and draft-23 the cancel closes the FETCH request stream and stops the fetch data stream. Delivery must then stop. A relay that refuses FETCH is reported, and the test does not fail.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Objects: 600 of 2048 bytes, 10 per Group, cached by the relay (max cache duration 60 s)¶

  • FETCH range: 0/0..59/9¶

  • Settle time after the cancel: 500 ms; observation time: 1 s¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |------ PUBLISH ------->|                       |
    |<----- REQUEST_OK -----|                       |
    |==== 600 Objects =====>|                       |
    |                       |<-- FETCH 0/0..59/9 ---|
    |                       |------ FETCH_OK ------>|
    |                       |==== first Object ====>|
    |                       |<---- cancel FETCH ----|
    |                       |                       * wait 500 ms
    |                       |                       * watch 1 s
¶

Expected Outcome:¶

  • The first Object arrives within 5 s.¶

  • No Object arrives in the 1 s observation period.¶

  • Fewer than 600 Objects are delivered in total.¶

5.11. Client GOAWAY

Applicability:

draft-18 and later¶

Description:

A client sends GOAWAY without a New Session URI. The relay is not required to respond; the test checks that a wire-valid GOAWAY is sent and that the session starts draining.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • New Session URI: none¶

Call Flow:¶

 Client                   Relay
    |                       |
    |------- GOAWAY ------->|
    * session closing
¶

Expected Outcome:¶

  • After sending GOAWAY the session is in the closing state.¶

5.12. Session Close Codes

Applicability:

draft-18 and later¶

Description:

A client closes its session with a given Session Termination code. The code must be carried in the WebTransport close. The relay may close the connection in response; that is allowed.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Case 1: code NO_ERROR (0x0), reason "test done"¶

  • Case 2: code PROTOCOL_VIOLATION (0x3), reason "e2e-injected"¶

Call Flow:¶

 Client                   Relay
    |                       |
    |--- WT close(code) --->|
    * session ended
¶

Expected Outcome:¶

  • The close completes without an error.¶

  • The session ends in the closed (none) state.¶

5.13. Session Termination and Migration

Applicability:

draft-18 and later¶

Description:

These cases check how the client handles the end of a session without needing the relay to end it. GOAWAY with a New Session URI is delivered to the client locally, as if the relay had sent it.¶

Inputs:¶

  • Delivery profiles: stream and datagram (run once each)¶

  • Case 1: the client closes its own session¶

  • Case 2: GOAWAY with New Session URI https://alt-relay.example/moq and a 5 s timeout, delivered to the client locally¶

  • Case 3: the client is asked to migrate to https://foo.example/moq without the worker it needs for migration¶

Call Flow:¶

 Client                   Relay
    |                       |
    * case 1: close(), no session-terminated
    |                       |
    * case 2: GOAWAY delivered locally;
    *         New Session URI held
    |                       |
    * case 3: migrate() refused
¶

Expected Outcome:¶

  • Case 1: no session-terminated event is raised for a close the client started.¶

  • Case 2: the client records the New Session URI as its pending migration target and moves to the closing state.¶

  • Case 3: the migration request is refused with an error that names the missing worker mode.¶

5.14. SETUP Options

Applicability:

draft-18 and later¶

Three tests on the Setup Options carried in CLIENT_SETUP and SERVER_SETUP.¶

5.14.1. Unknown Client Setup Options Are Ignored

Description:

The client advertises two Setup Options with unregistered keys. A peer is required to ignore unknown Setup Options (Section 6.3.2 of [MoQTransport22]), so the relay must still complete the setup exchange.¶

Inputs:

  • Setup Option 0x40 (even key): varint 0x1234.¶

  • Setup Option 0x41 (odd key): bytes "moq-web-e2e".¶

Call Flow:¶

 Client                           Relay
    |                               |
    |-- CLIENT_SETUP -------------->|
    * carries options 0x40 and 0x41
    |<-------------- SERVER_SETUP --|
    * session ready
    |                               |
¶
Expected Outcome:

  • SERVER_SETUP is received and the session reaches the ready state.¶

5.14.2. Relay Setup Options Are Well Formed

Description:

The client records the Setup Options the relay advertises in SERVER_SETUP. A relay that advertises none passes.¶

Inputs:

  • None beyond a plain CLIENT_SETUP.¶

Call Flow:¶

 Client                           Relay
    |                               |
    |-- CLIENT_SETUP -------------->|
    |<-------------- SERVER_SETUP --|
    * list each option and its value kind
    |                               |
¶
Expected Outcome:

  • Every option with an even key carries a varint.¶

  • Every option with an odd key carries a byte string.¶

5.14.3. Client Setup Options Are Fixed After Setup

Description:

Once setup has run, the client must not change the Setup Options it advertised. This is a local check made on a live session; nothing is sent to the relay for it.¶

Inputs:

  • Setup Option 0x40, set after SERVER_SETUP.¶

Call Flow:¶

 Client                           Relay
    |                               |
    |-- CLIENT_SETUP -------------->|
    |<-------------- SERVER_SETUP --|
    * try to set option 0x40: refused locally, nothing sent
    |                               |
¶
Expected Outcome:

  • The attempt to change Setup Options after setup fails locally.¶

5.15. TRACK_STATUS Reports the Largest Object

Applicability:

draft-18 and later¶

Description:

A publisher sends three Objects, then a second session asks the relay for the Track status (Section 9.13 of [MoQTransport22]). The relay may answer from its own state or forward the request; only the answer is checked. A REQUEST_ERROR is tolerated.¶

Inputs:

  • Track: <ns>/chat, stream delivery.¶

  • Objects 0/0, 1/0 and 2/0, one per Group.¶

  • A 250 ms wait before TRACK_STATUS.¶

Call Flow:¶

   Pub                    Relay                    Req
    |                       |                       |
    |-- PUBLISH ----------->|                       |
    |<-------- REQUEST_OK --|                       |
    |== g0/o0 g1/o0 g2/o0 =>|                       |
    * wait 250 ms
    |                       |<------ TRACK_STATUS --|
    |                       |-- REQUEST_OK -------->|
    |                       |       LARGEST_OBJECT  *
    |                       |                       |
¶
Expected Outcome:

  • The answer is REQUEST_OK with a Request ID, or REQUEST_ERROR (the test then ends).¶

  • If LARGEST_OBJECT (Section 9.20.17 of [MoQTransport22]) is present, its Group and Object are non-negative.¶

5.16. NAMESPACE_DONE Ends a Namespace Batch

Applicability:

draft-18 and later¶

Description:

A subscriber sends SUBSCRIBE_NAMESPACE for a prefix with no publishers. The relay may close the initial batch with NAMESPACE_DONE (Section 9.17 of [MoQTransport22]) or keep the request open for later NAMESPACE messages; both are accepted.¶

Inputs:

  • Prefix: moq-web-e2e/chat-stream/ns-done.¶

  • A 500 ms wait for NAMESPACE and NAMESPACE_DONE.¶

Call Flow:¶

 Client                           Relay
    |                               |
    |-- SUBSCRIBE_NAMESPACE ------->|

5.42. FETCH from the Relay Cache

Applicability:

draft-22 and later¶

Description:

A holder subscription keeps groups 0..2 in the relay's cache, then a second session fetches them in five shapes. Every Object is checked byte for byte. MOQT sets no cache size, so the test caches only 3 groups, which the smallest relay cache seen keeps per track. A FETCH end location is inclusive (Section 9.11 of [MoQTransport22]), and a FETCH ends at the Largest Object, so Objects published after it are not part of the response (Section 3.2 of [MoQTransport]).¶

Inputs:

  • Track <ns>/t, stream delivery, MAX_CACHE_DURATION 60 s.¶

  • Cached: groups 0..2, 3 Objects each (Object IDs 0..2).¶

  • The five cases in the table below.¶

Table 1: FETCH cases
Case FETCH range Variation Expected Objects
whole 1/0..2/0 none 1/0..2/2 (6)
partial 0/1..1/1 none 0/1..1/1 (4)
descending 0/0..1/0 group order descending 0/0..1/2 (6), groups 1, 0
cache-only 0/0..2/0 Pub closes its session first 0/0..2/2 (9), or DOES_NOT_EXIST
live-edge 1/0..4/0 Pub sends groups 3..4 after the FETCH 1/0..2/2 (6)

   Pub                    Relay              Holder / Sub
    |                       |                       |
    |-- PUBLISH <ns>/t ---->|                       |
    |                       |<-- SUBSCRIBE (Holder)-|
    |== g0..g2, 3 obj =====>|== g0..g2 ============>| Holder
    |                       |                       * wait 500 ms
    * [cache-only] close    |                       |
    |                       |<-- FETCH (Sub) -------|
    |                       |   range of the case   |
    * [live-edge] g3..g4    |                       |
    |== g3..g4 ============>|                       |
    |                       |-- FETCH_OK ---------->|
    |                       |== fetch stream ======>| Sub
    |                       |   Objects in range    |
¶
Expected Outcome:

  • No FETCH error, except that cache-only may instead get REQUEST_ERROR DOES_NOT_EXIST with no Objects.¶

  • Every expected Object in the table arrives, byte for byte.¶

  • No Object outside the range arrives; in live-edge, none of groups 3..4.¶

  • In descending, groups arrive in descending order.¶

  • At least 10 Objects arrive at Sub in the 2 s after GOAWAY.¶

  • PUBLISH_DONE arrives within 5 s of the track ending.¶

5.48. Object Properties

Applicability:

draft-22 and later¶

Description:

Every Object carries two Object Properties of types the relay does not know, one even (varint) and one odd (bytes). Both are below the Mandatory range, so the relay must forward them unchanged (draft-22 Section 11.1).¶

Inputs:

  • Track <ns>/t, stream delivery.¶

  • 3 groups of 4 Objects.¶

  • Property 0x40 = group x 100 + object (varint).¶

  • Property 0x41 = p<G>/<O> (bytes).¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |-- PUBLISH <ns>/t ---->|                       |
    |                       |<-- SUBSCRIBE <ns>/t --|
    |                       |-- SUBSCRIBE_OK ------>|
    |                       |                       * wait 200 ms
    |== g0..g2, o0..o3 ====>|== g0..g2, o0..o3 ====>|
    |   props 0x40, 0x41    |   props unchanged     |
    |                       |                       * wait <= 5 s
¶
Expected Outcome:

  • All 12 Objects arrive.¶

  • Each carries 0x40 = group x 100 + object and 0x41 = p<G>/<O>.¶

5.49. Setup Options and Concurrent REQUEST_UPDATEs

Applicability:

draft-22 and later¶

Description:

The Setup Options in the relay's SERVER_SETUP must be well formed, and the relay must honour MAX_REQUEST_UPDATES (Section 9.1.7 of [MoQTransport22]): the subscriber sends that many REQUEST_UPDATEs at once on one subscription, and each must be answered in order.¶

Inputs:

  • Track <ns>/t.¶

  • Updates sent at once: the relay's MAX_REQUEST_UPDATES, capped at 4; 4 if the relay sets no limit.¶

  • The updates alternate pause and resume.¶

Call Flow:¶

   Pub                    Relay                    Sub
    |                       |                       |
    |                       |<-- CLIENT_SETUP ------|
    |                       |-- SERVER_SETUP ------>|
    |                       |   Setup Options       |
    |                       |                       * check options
    |-- PUBLISH <ns>/t ---->|                       |
    |                       |<-- SUBSCRIBE <ns>/t --|
    |                       |-- SUBSCRIBE_OK ------>|
    |                       |<-- REQUEST_UPDATE #0 -|
    |                       |<-- REQUEST_UPDATE #1 -|
    |                       |<-- ...  #N-1 ---------|
    |                       |------ REQUEST_OK ---->| #0
    |                       |------ REQUEST_OK ---->| #1
    |                       |-- ...               ->| #N-1
¶
Expected Outcome:

  • Every Setup Option with an even key carries a varint, and every one with an odd key carries bytes.¶

  • Every REQUEST_UPDATE is answered within 5 s.¶

  • The REQUEST_OKs arrive in the order the updates were sent.¶
